# dev-issue

개인 프로젝트에서 반복되는 "기능 개발"과 "버그 수정"을 절차화한 스킬. 핵심 원칙: 테스트가 코드보다 먼저 나온다. 모호하면 멈추고 사람에게 묻는다 — 특히 기능 개발은 요구사항 대화가 본질이라, 이 단계를 생략하고 무인으로 끝까지 진행하지 않는다.

## 0. 입력 파악

- 인자가 이슈 번호면 `gh issue view <번호> --json title,body,labels`로 내용을 가져온다.
- 인자가 자유 텍스트 설명이면 그대로 사용한다.
- `bug`/`feature` 라벨이 있으면 유형으로 신뢰한다. 라벨이 없거나 애매하면 사람에게 유형을 확인한다.

## 1. 명확화 (건너뛰지 않는다)

- **버그**: 재현 조건(입력/환경/기대 동작 vs 실제 동작)이 명시되어 있는지 확인한다. 빠져 있으면 추측하지 말고 질문한다.
- **기능**: 인수 조건(무엇이 되면 "완료"인지)이 불명확하면 질문한다. 여러 해석이 가능하면 각각을 제시하고 고르게 한다.

## 2. 테스트 먼저 작성

- **버그 수정**: 버그를 재현하는, 지금 시점엔 반드시 실패하는 테스트를 먼저 작성한다.
- **기능 개발**: 1번에서 확정한 인수 조건을 검증하는 테스트를 작성한다.
- 기존 테스트 스타일/러너를 그대로 따른다 (새 프레임워크 도입 금지).

## 3. 구현

- 필요한 최소한의 코드만 작성한다. 요청받지 않은 리팩토링/개선은 하지 않는다.
- 수정 범위가 이슈에서 벗어나기 시작하면 멈추고 알린다.

## 4. 검증

- 새로 작성한 테스트가 통과하는지 확인한다.
- 전체 테스트 스위트를 돌려 회귀가 없는지 확인한다. 실패하면 원인을 고치고 그린이 될 때까지 반복한다.
- 빌드/린트가 있으면 함께 확인한다.

## 5. PR

- `gh pr create --draft`로 draft PR을 연다. 본문에 어떤 이슈를 처리했는지, 어떤 테스트로 검증했는지 적는다.
- 절대 머지하지 않는다. 이 스킬의 종료 지점은 draft PR 생성까지다.

## 하지 않는 것

- 이슈 유형/재현조건/인수조건이 애매한데 임의로 추측해서 진행하는 것.
- 자동 머지, 강제 푸시, 브랜치 삭제 등 되돌리기 어려운 작업.
- 사람과의 명확화 대화 없이 기능 개발을 처음부터 끝까지 무인으로 진행하는 것 — 이건 이 스킬의 설계 범위 밖이다 (사람이 세션에 붙어 있는 상태에서만 쓴다).
